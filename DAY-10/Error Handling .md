# ❌ Error Handling in Lightning Web Components (LWC)

## 📌 Overview

Error handling is an important part of building reliable Lightning Web Components.

In a real-world Salesforce application, operations can fail for many reasons:

* Invalid user input
* Validation rule failures
* Salesforce permission issues
* Apex exceptions
* SOQL errors
* Network or server problems
* Missing records
* Incorrect parameters
* Data access restrictions
* Unexpected application errors

A good LWC should not simply fail when an error occurs. It should:

```text
Detect Error
    ↓
Understand Error
    ↓
Handle Error
    ↓
Update Component State
    ↓
Display Meaningful Message
    ↓
Allow User to Recover
```

---

# 🎯 Why Error Handling Is Important

Without proper error handling:

```text id="8qk4rs"
User Action
    ↓
Error Occurs
    ↓
Application Stops / Blank UI ❌
```

With proper error handling:

```text id="p6ckm5"
User Action
    ↓
Error Occurs
    ↓
Error Detected
    ↓
Error Processed
    ↓
User-Friendly Message
    ↓
User Can Correct / Retry
```

Good error handling improves:

* User experience
* Application reliability
* Debugging
* Maintainability
* Data integrity
* Developer productivity

# 🧩 1. Types of Errors in LWC

Errors can occur at different levels of an application.

```text id="6z8h5x"
                    LWC Application
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   Client Error       Salesforce Error    Apex Error
        │                 │                 │
        ▼                 ▼                 ▼
   JavaScript         LDS / Validation    Exceptions
```

Common categories include:

### Client-Side Errors

Errors caused by JavaScript logic or invalid component state.

### LDS Errors

Errors returned while working with Salesforce records through Lightning Data Service.

### Apex Errors

Errors generated by server-side Apex logic.

### Validation Errors

Errors caused by Salesforce validation rules or invalid field values.

### Permission Errors

Errors caused when a user does not have the required access.

---

# 🖥️ 2. Client-Side Error Handling

Client-side errors can occur because of incorrect JavaScript logic, invalid data, or unexpected values.

Example:

```javascript id="5fukz3"
try {
    const result = this.total / this.quantity;
} catch (error) {
    console.error(error);
}
```

A safer approach is to validate values before processing them.

```javascript id="xikf7u"
if (!this.quantity || this.quantity <= 0) {
    this.errorMessage = 'Please enter a valid quantity.';
    return;
}
```

### Best Practice

Do not allow invalid input to reach server-side processing when it can be detected on the client.

---

# ☁️ 3. Handling Apex Errors

When an LWC calls Apex, the operation can succeed or fail.

```text id="plm2qf"
LWC
 ↓
Apex
 ↓
 ┌──────────────┐
 │              │
Success        Error
 │              │
 ▼              ▼
Data          Handle Error
```

Example:

```javascript id="2c5k0j"
import getAccounts from '@salesforce/apex/AccountController.getAccounts';

getAccounts()
    .then(result => {
        this.accounts = result;
        this.error = undefined;
    })
    .catch(error => {
        this.accounts = undefined;
        this.error = this.reduceError(error);
    });
```

The `.catch()` block handles the rejected Apex request.

---

# ⚠️ 4. Apex Exception Handling

Apex should also handle errors appropriately.

Example:

```apex id="qu0v2h"
public with sharing class AccountController {

    @AuraEnabled
    public static List<Account> getAccounts() {
        try {
            return [
                SELECT Id, Name
                FROM Account
                LIMIT 50
            ];
        } catch (Exception e) {
            throw new AuraHandledException(
                'Unable to retrieve account information.'
            );
        }
    }
}
```

The purpose of handling the exception in Apex is to return a controlled error to the LWC.

### Flow

```text id="2v9f0h"
LWC
 ↓
Apex
 ↓
Exception
 ↓
Apex Handles Error
 ↓
Controlled Error Response
 ↓
LWC
 ↓
Display Message
```

# 🗄️ 5. Handling Lightning Data Service Errors

LDS operations can also produce errors.

For example:

```text id="mpp4gy"
Create / Update / Delete Record
           ↓
       LDS Operation
           ↓
      ┌────┴────┐
      ▼         ▼
   Success     Error
      │         │
      ▼         ▼
  Continue   Handle Error
```

Example:

```javascript id="5a70he"
handleError(event) {
    const error = event.detail;

    this.errorMessage =
        'Unable to save the record. Please check the entered values.';
}
```

The exact error structure depends on the LDS component or API being used.

# 📝 6. Validation Errors

Salesforce validation rules can prevent records from being saved.

Example validation rule:

```text id="8n4b0y"
Amount must be greater than 0
```

The user enters:

```text id="3c3f7q"
Amount = -500
```

Salesforce rejects the operation.

```text id="2jdrs7"
User Input
    ↓
LWC
    ↓
Salesforce Validation
    ↓
Validation Error
    ↓
Display Error
```

### Best Practice

Where possible, validate obvious input problems in the UI before submitting the request.

However, Salesforce server-side validation must still be respected because client-side validation alone cannot guarantee data integrity.

# 🔐 7. Permission and Access Errors

A user may not have permission to:

* Read an object
* Read a field
* Edit a record
* Create a record
* Delete a record

Example:

```text id="l8s4t5"
User Attempts Update
        ↓
Salesforce Security
        ↓
No Required Permission
        ↓
Error
        ↓
User-Friendly Message
```

A production application should handle these errors gracefully.

### Example Message

```text id="4z2r0j"

```

Avoid exposing unnecessary technical information to end users.

# 📢 9. Displaying User-Friendly Errors

Technical error messages are often difficult for users to understand.

### Avoid

```text id="0qz3ac"
System.NullPointerException at line 45
```

### Prefer

```text id="1l5v0f"
Unable to save the account. Please check the information and try again.
```

The developer can still log the technical details for debugging while showing a simple message to the user.

# 🔔 10. Toast Notifications

Toast messages are commonly used to provide quick feedback.

Example:

```javascript id="0dd0wt"
import { ShowToastEvent } from 'lightning/platformShowToastEvent';

showError() {
    const event = new ShowToastEvent({
        title: 'Error',
        message: 'Unable to save the record.',
        variant: 'error'
    });

    this.dispatchEvent(event);
}
```

A successful operation can also use a success toast:

```javascript id="f2ov9v"
const event = new ShowToastEvent({
    title: 'Success',
    message: 'Record saved successfully.',
    variant: 'success'
});

this.dispatchEvent(event);
```

### Typical UI Feedback

```text id="4yg4y9"
Success → Green / Success Notification
Error   → Error Notification
Warning → Warning Notification
Info    → Information Notification
```

# 🧹 11. Centralized Error Processing

Different Salesforce APIs may return errors in different structures.

Instead of repeatedly processing errors throughout the application, a reusable error-processing function can be created.

Example:

```javascript id="3qgy9y"
reduceError(error) {
    if (!error) {
        return 'Unknown error occurred.';
    }

    if (Array.isArray(error.body)) {
        return error.body.map(e => e.message).join(', ');
    }

    return error.body?.message ||
           error.message ||
           'Unknown error occurred.';
}
```

Then components can use:

```javascript id="nq1q0g"
this.errorMessage = this.reduceError(error);
```

### Benefits

* Less duplicate code
* Consistent error messages
* Easier maintenance
* Easier testing
* Cleaner components

# 🔁 12. Error Recovery and Retry

Good error handling should provide a recovery path when possible.

Example:

```text id="b8gz0m"
Request
  ↓
Error
  ↓
Display Message
  ↓
Retry
  ↓
Request Again
```

For example:

```text id="d4tz7g"

[ Retry ]
```

The user can retry instead of refreshing the entire Salesforce page.

# 🧠 13. Error Handling with Component Communication

Errors may need to move between components.

Example:

```text id="2r77ep"
Child Form
    ↓
Save Failed
    ↓
Custom Event
    ↓
Parent Component
    ↓
Display Error
```

The child can dispatch an error event:

```javascript id="y7r3f4"
this.dispatchEvent(
    new CustomEvent('error', {
        detail: {
            message: 'Unable to save account.'
        }
    })
);
```

The parent can handle it:

```javascript id="l8i4ts"
handleError(event) {
    this.errorMessage = event.detail.message;
}
```

This allows the parent to coordinate application-level error handling.

Conceptually:

       ┌──────────┼──────────┐

# ⚡ 19. Error Handling Best Practices

## ✅ Do

* Validate user input.
* Handle Apex errors.
* Handle LDS errors.
* Handle validation failures.
* Display meaningful messages.
* Log useful technical information.
* Reset error state when appropriate.
* Provide retry or recovery options.
* Keep error handling reusable.
* Consider loading, success, error, and empty states.

## ❌ Avoid

* Ignoring errors.
* Showing raw technical exceptions to users.
* Using empty `catch` blocks.
* Hiding errors from users.
* Duplicating the same error-processing logic everywhere.
* Assuming every request will succeed.
* Relying only on client-side validation.
* Exposing sensitive information in error messages.

# 📊 21. Error Handling Strategy

| Error Type       | Example                | Recommended Handling         |
| ---------------- | ---------------------- | ---------------------------- |
| Client Error     | Invalid input          | Validate and display message |
| LDS Error        | Record update failure  | Handle error response        |
| Apex Error       | Server exception       | Catch and process error      |
| Validation Error | Required field missing | Display validation message   |
| Permission Error | No edit access         | Show access message          |
| Network Error    | Request failure        | Show retry option            |
| Empty State      | No records found       | Display empty-state message  |

# 🏆 22. Key Takeaways

Error handling should be treated as part of the application architecture rather than as an afterthought.

A reliable LWC application should follow:

```text id="e6k1n8"
Validate
   ↓
Process
   ↓
Handle Success
   ↓
Handle Error
   ↓
Update State
   ↓
Refresh UI
```

The most important principles are:

1. **Always expect operations to fail.**
2. **Handle errors at the appropriate layer.**
3. **Keep technical details separate from user-facing messages.**
4. **Use reusable error-processing logic.**
5. **Provide users with a clear recovery path.**
6. **Keep the UI state consistent after failures.**
7. **Test both success and failure scenarios.**

---

# 🚀 Final Takeaway

Error handling is essential for transforming an LWC from a simple working component into a **production-ready Salesforce application**.

The goal is not simply to prevent errors. The goal is to ensure that when something goes wrong:

```text id="f3u8e6"
Error Occurs
     ↓
Application Detects It
     ↓
Application Handles It
     ↓
State Remains Consistent
     ↓
User Understands What Happened
     ↓
User Can Recover
```

> **A good LWC does not assume that everything will work. It prepares for failure, handles errors gracefully, keeps the UI consistent, and gives the user a clear path forward.**
